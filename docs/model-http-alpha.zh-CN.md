# 仅依赖模型：HTTP 接入（开发者 · A测）

本分支为 `codex/model-http-alpha`，不合并 main，不包含部署操作。面板和模型是两个独立进程，可以在不同机器运行，通过 HTTP 请求与 JSON 响应通信，无须同机部署。

## 检查点

使用训练聊天中最后明确选择的 **Anomaly Transformer Epoch 58**，保留第 27 局作为该检查点的留出评估数据。Epoch 128 饱和检查点曾用第 27 局训练，随后被用户明确退回，本分支不将它冒充已选择的模型。

权重、固定 scaler 和哈希清单在 `services/integrity-model/artifacts/`；启动时核验 SHA-256，再以 `weights_only=True` 加载。上传的检查点只包含 state_dict、轮次和随机种子，不包含原始玩家数据、服务器密码或训练快照。

模型结构来自 [THUML Anomaly-Transformer](https://github.com/thuml/Anomaly-Transformer)，保留 MIT 许可证。适配仅将强制 CUDA 的距离张量改为随模型设备移动的非持久 buffer，权重未修改。加载方式参考 [PyTorch 序列化文档](https://docs.pytorch.org/docs/stable/notes/serialization.html)。

## 配置入口

组织管理 → 风控设置 → **开发者模型 · A测**：

1. 填写独立模型服务根地址，例如 `http://model-host:8091`。
2. 填写与模型服务一致的 32 字符以上令牌。数据库加密存储，页面不回显；留空保留。
3. 设置请求间隔、每小时处罚上限与玩家处罚冷却，勾选自动处罚，启用开发者状态并保存。
4. 测试连接，核对模型 ID、权重哈希及输入版本。
5. 在评估模式中选择 **仅依赖模型（开发者 · A测）**。

新模式会跳过旧评分与五专家投票，但继续保存模型所需的观测特征。HTTP 请求在独立持久化队列中执行，不阻塞 Feed；同一玩家、对局、时间段、配置版本去重。关闭开发者状态后不再发送请求；修改配置或模式会使旧队列结果失效。连接失败不回退专家，不记为正常。队列中断超过五分钟标记 ERROR，可在下一请求间隔重试。

按用户指定自动处罚：**分数达到 P95 自动踢出；达到 P99 优先隔离 24 小时并踢出**。百分位基于 Epoch 58 的 991 个训练窗口重构分数，第 27 局不参与计算；P95 = 0.012539893854409456，P99 = 0.04076347462832935。参考数据未标注，不能宣称是已验证正常玩家分布或作弊概率。固定参考清单与哈希随模型发布，双方核验，服务端独立比较分数，不能由模型 API 指定任意处罚。

选择模型模式并开启开发者状态与自动处罚后，单靠模型分数触发，无需专家投票或旧评分。处置前与实际踢人前检查配置、玩家身份、在线状态和新鲜观测，VIP 白名单免除；预留位和免 KD/KPM 不单独豁免模型处罚。默认每组织每小时最多 10 次、同玩家冷却 600 秒，可配置。P99 允许从近期 P95 踢出升级隔离。隔离写入现有服务器封禁名单，24 小时到期自动失效；管理员可提前撤销。人工封禁不覆盖、不缩短。已经生效的隔离不因关闭模型开关而自动删除。

处罚与模型记录关联，页面区分入队、送达、跳过、失败、结果未知。结果未知不自动重发；同一评分只处罚一次。先完成评分写入、再处置时意外中断，会恢复尚未处置的有效记录。现有人工管理与其他独立规则继续保留。

## 输入与限制

- 使用原训练特征构建器：每桶 30 秒、每窗口 200 桶，同一玩家同一局，约 100 分钟。
- 所有桶须有活动，至少 80% 桶有观测、75% 桶有现金观测；不足返回 `INSUFFICIENT_DATA`。
- 固定使用训练 scaler，缺失值携带原有 mask，不把缺失当作实际零值。
- 27 通道不包含武器、距离、命中部位，也不输出“作弊概率”。
- 实时接口发送最近约 102 分钟的玩家进度、窗口观测及可用历史指标；玩家标识替换为 `player`，不发昵称、SteamID、专家投票或标签。保留人数，避免过滤单玩家后错误变成 1 人服务器。
- 原训练可能包含额外原始轮询快照；实时接口以持久化进度表为准，缺失保留，需通过 A测确认与训练分布的差异。
- 输入最多 8 MiB，每张来源表最多 25000 条；超限拒绝而非悄悄截断。HTTP 超时 30 秒，响应最多 64 KiB，禁止重定向。
- 结果在组织风控页保留最近 50 条供查看；迁移 `0069_model_alpha.sql` 创建结果/队列表。

## 独立服务与 API

以后需要部署时，单独构建 `services/integrity-model/Dockerfile`，设置 `MODEL_API_TOKEN`。本次只提交和构建，不启动线上服务。

本地开发：Python 3.12，安装 requirements.txt，设置 `MODEL_API_TOKEN` 后运行 `python server.py`。默认绑定 `127.0.0.1:8091`；容器绑定 `0.0.0.0:8091`。HTTP 可用于可信内网，公网连接使用 HTTPS 反向代理。

所有模型请求使用 `Authorization: Bearer <token>`：

| 接口 | 用途 |
| --- | --- |
| `GET /v1/health` | 返回模型 ID、轮次、权重哈希、输入版本 |
| `POST /v1/assess` | 接收特征来源，返回 READY / INSUFFICIENT_DATA 及评分 |

请求形状：`{schema: "warcon-raw-30s-v1", requestId: "唯一ID", sources: {matches: [...], player_progress_samples: [...], integrity_player_metric_history: [...], integrity_windows: [...]}}`。单请求限一局、一名玩家；来源字段见模型目录 `test_inference.py` 的可运行合成示例。

面板管理接口 `GET/PUT/POST /api/orgs/:id/integrity/model` 分别读取配置与结果、保存配置、测试连接，均要求组织 owner 权限；API 请求遵守面板现有会话/组织 Key 和 CSRF 规则。

GitHub workflow **A测 model HTTP build** 只测试、构建镜像并保存下载包，不推送部署目标、不发布镜像、不合并分支。
